1. REVIEW OF MORROW'S PLAIN-ENGLISH EXPLANATION

Morrow's overall division of responsibility is right: Core coordinates the network
on Velocity; Hub provides the Paper interface; Interact supplies optional world
entry points; a provider runs the backend process. Ordinary backends do not need
HubPilot plugins just for requests or power control. They still require their
platform's forwarding support. Core is not a Minecraft process host.

The explanation needs these qualifications:

IMPLEMENTED: Core's normal join admission checks maintenance, the configured
server permission and optional strict client version. Those checks use the actual
Velocity player. A display name, managed ID, Velocity name, provider definition ID
and provider server ID are distinct identifiers. A WORLD request opcode does not
prove Core can switch arbitrary worlds inside one Minecraft process: the inspected
request handler resolves its target through the managed-server lifecycle.

IMPLEMENTED: queues are per-server startup waiting lists, not a network-wide
scheduler or a backend-full admission queue. One StartSession is shared per managed
server ID, using putIfAbsent. A LinkedHashSet preserves insertion order and avoids
repeating the same UUID in that one queue. There is no general one-outstanding-
request-per-player rule across servers in LifecycleManager.

IMPLEMENTED: online destinations bypass startup countdown. When cached status is
online, Core connects immediately. Otherwise it performs a Minecraft status ping;
a successful ping also leads directly to connection. Only the queued startup path
enters its STARTING -> COUNTDOWN sequence. Queue positions do not mean one player
is admitted at a time: the countdown completion iterates the waiting players and
issues connection requests for them.

IMPLEMENTED: provider acceptance and readiness differ. A successful start HTTP
response sets startAccepted, but tickSession advances based on StatusStore.online().
The inspected transition does not require startAccepted to be true. Readiness is
successful Minecraft status reachability, not a successful authenticated player
login, mod handshake, forwarding-secret check or proof that a particular game mode
has finished initialization. Link's ready telemetry is not the lifecycle gate.

IMPLEMENTED: cancellation removes a UUID from startup/countdown queues. It does
not cancel an already issued provider request, every in-flight initial ping, or
scheduled connection retries. Reconnect-resistant cooldowns and request-generation
cancellation are not implemented here. A successful ServerPostConnect event removes
the player from all queues, even when the connection is to another destination.

IMPLEMENTED: startup timeout, connection retry delay and countdown are separate.
The default retry count of three means an initial connection attempt plus up to
three retries. It is not three provider-start retries. There is no inspected
application-level HTTP retry loop in the provider action transport.

IMPLEMENTED / UNCERTAIN: automatic stopping has useful safeguards, but describing
it as complete demand accounting would overstate the code. Idle shutdown checks
queue size and pending transfers. The final automatic stopServer guard checks
configured-hub identity, players connected through this Velocity instance, and a
controllable provider. It does not universally recheck all current queues,
pending transfers, request generations, or the latest Always-On setting.

IMPLEMENTED: configured-hub protection is stronger than ordinary Always-On
protection against stale session definitions: the final automatic dispatcher checks
the current config as well as the passed definition. Always-On ordinarily works
by turning off shutdown flags in the effective ManagedServer. A stale non-hub
session is a separate risk, not evidence that the hub repair is missing.

IMPLEMENTED: Link supplies telemetry and component presence. The detailed OP,
permission and role report used by Core comes from Hub's PublicHubBootstrap AUTH
messages. Do not describe Link as the sole authorization bridge.

IMPLEMENTED / DOCUMENTATION DISCREPANCY: the September 3 automatic hub repair does
not change manual provider power methods. However, ServerAdminBridge's SERVER_STOP
GUI path explicitly refuses to stop the configured hub from the hub, and rejects
connected players. Thus the docs' broad statement that manual hub stop remains
available must not be translated into a promise that this GUI action allows it.
Inspect the actual chosen manual route; panel-side manual power remains outside
Core's automatic-stop guard. This audit did not live-test manual hub shutdown.

LifecycleManager storage and identity:
  sessions: ConcurrentHashMap<String,StartSession>, keyed by managed server ID.
  transferPermits: ConcurrentHashMap<UUID,TransferPermit>.
  lastActivity: ConcurrentHashMap<String,Long>.
  pendingTransfers: ConcurrentHashMap<String,Set<UUID>>.
  StartSession captures one ManagedServer object and startedAt. It has a synchronized
    LinkedHashSet<UUID> queue and position map; phase/timing flags are volatile.
  Session phases are STARTING and COUNTDOWN; separately, StatusStore states are
    UNKNOWN, OFFLINE, STARTING, ONLINE, STOPPING and MAINTENANCE.
  There is no durable queue or
    persisted request/session ledger, request nonce or distributed lock.
  Session identity uses object identity/conditional map removal, not a generation
    carried through all asynchronous callbacks.

Normal request algorithm (IMPLEMENTED):
  1. Reject null/inactive player, unknown ID/Velocity name, maintenance, missing
     configured server permission or strict protocol mismatch; report already there.
  2. Increment request counter. If cached online, connect immediately.
  3. Require Velocity registration. Ping with the server's ping timeout.
  4. On successful ping set online and connect. On failed ping, queueAndStart.
     Callback checks player active, but not a cancellation generation/current target.
  5. Require autostart and a managed enabled provider. putIfAbsent shares a server
     session. First requester sets STARTING, queues, records messages/counters and
     submits provider start. Later requesters join the same session.
  6. tick runs each second. It ignores a session replaced/removed from sessions.
     An empty queue with stopWhenQueueEmpty removes/stops it. STARTING timeout is
     elapsed wall time since session creation, not since provider acknowledgement.
  7. Once status.online is true, record startup success and enter COUNTDOWN.
     Zero seconds finishes immediately. Otherwise calculate remaining seconds from
     the deadline, send feedback and eventually finishCountdown.
  8. finishCountdown conditionally removes the session, clears queue count, and
     starts connections for active queued players. No per-player capacity pacing.
  9. connect records pending demand and a 10-second UUID/Velocity-target permit.
     The permit permits the matching internal preconnect once, preventing recursion.
     It is not a durable authorization token or a cryptographic network credential.
  10. Successful transfer records counters/activity and removes pending demand.
      Failure schedules retry while active until the configured retry count is
      exhausted, then optionally requests failed-connection cleanup.

Admission convergence and exceptions:
  Navigator/Interact use Hub's normal destination request sender, which ends at
    Core LifecycleManager.request after transport trust validation.
  /hp request uses LifecycleManager.request after the command layer's gates.
  intercepted direct Velocity requests validate admission and queue an offline
    managed target through request; online/always-online cases can pass directly.
  testStart is a separate administrative power test; it does not implement the
    complete player admission/countdown lifecycle.
  manual server stop is also a separate administrative provider path.
  lifecycle interception can be disabled. The inspected request method itself
    does not contain the command layer's complete setup/role gating.
Do not claim that every entrypoint already executes one identical authorization
function. Tests must compare command, plugin-message, direct-connect and admin paths.

Cancellation, retries and concurrency limits:
  cancel removes queue membership across sessions and reports whether it found any.
  disconnect removes queues with empty-queue cleanup enabled.
  postconnect updates current backend activity and removes queues with that immediate
    cleanup flag disabled; a later tick may still clean an empty startup session.
  There are no retained retry ScheduledTask handles to cancel here. The retry lambda
    checks isActive(), then reconnects to its captured target/definition.
  pendingTransfers is a UUID set, not a count of all simultaneous attempts; overlapping
    attempts for the same player/target can collapse into one set membership.
  shutdown clears maps but does not visibly cancel every already-issued HTTP/ping/
    connect future. Verify late callbacks during proxy shutdown in a runtime harness.
  Reload replaces config snapshots; existing sessions/retries retain captured rules.
  A configured hub is rechecked at the final automatic stop boundary using current
    config. Ordinary maintenance/permissions/Always-On are not uniformly refreshed
    immediately before each connection/stop.

Safe automatic stopping, current scope:
  tickIdleShutdown skips configured hub, unmanaged provider, disabled idle timeout,
    offline/unregistered targets; queue, pending demand or proxy players refresh
    lastActivity. Crossing idle threshold calls stopServer.
  failStart conditionally removes its session and may call stopServer.
  stopAndRemove conditionally removes an empty session and calls stopServer.
  exhausted connect attempts may call stopServer after pending/player checks.
  stopServer rejects configured hub, then connected Velocity players, then unmanaged
    providers. It sets STOPPING and submits provider stop. Success sets OFFLINE and
    increments stops; failed HTTP logs an error. Polling is needed to observe reality.

Important limitations, IMPLEMENTED observations / UNCERTAIN operational impact:
  The final guard does not prove the server was started by this particular request.
  An already-running backend's failed join can reach failed-request cleanup.
  It does not check players arriving directly or via another proxy; the proxy's
    connected-player collection is not a network-wide population oracle.
  Queue-empty stop can race an outstanding provider start acknowledgement.
  Removing a session can race a fresh request that starts a replacement session.
  Countdown removal occurs before all pending transfer entries are inserted.
  Current player demand is not atomically locked with the external stop action.
  The final guard has no universal current-session/pending-demand check and no
    universal fresh Always-On check for stale non-hub definitions.
These are concrete test targets found by inspection, not newly reproduced player
incidents. Preserve hub protection while addressing them.

4. PROTOCOL, TRUST, AUTHORIZATION AND DATA OWNERSHIP

Wire convention (IMPLEMENTED): Java DataInputStream/DataOutputStream framing.
U below means Java modified UTF-8 writeUTF/readUTF, with an unsigned 16-bit encoded
byte length; I=int32, L=int64, D=double64, F=float32, B=boolean. These are ordered
binary fields, not JSON, newline text, standard UTF-8 strings or VarInts. Character
count limits do not guarantee modified-UTF byte limits for non-ASCII text.

hubpilot:request, Hub -> Core:
  U type, U target, optional U statusTarget.
  accepted type values case-insensitively: SERVER, WORLD, REQUEST, JOIN.
  target regex [A-Za-z0-9_-]{1,64}.
  Core reads/discards the optional third field for this path; it does not accept an
    arbitrary caller-supplied player UUID. Player identity is the carrier connection.
  REQUEST_CHANNEL and LEGACY_REQUEST_CHANNEL resolve to the same channel in 1.0.2.

hubpilot:control, bidirectional multiplexed messages:
  AUTH: U opcode, U carrierUUID, U username, B op, B admin, B moderator,
    B helper, B claimPermission. Hub sends it; Core binds UUID to the carrier.
  COMPONENT: U opcode, U carrierUUID, U componentName, U componentVersion.
    Name/version have 32-character checks; component presence is not authorization.
  ACTION: U opcode, U carrierUUID, U action, action-specific U fields.
    CLAIM_OWNER: username, op-as-text, claimPermission-as-text.
    STAFF_SET: targetUUID, username, role.
    OWNER_ADD: targetUUID, username. OWNER_REMOVE: targetUUID.
    PROVIDER_TYPE / PROVIDER_URL / PROVIDER_SECRET: one value.
    PROVIDER_TEST / PROVIDER_SKIP / SETUP_COMPLETE: no extra argument.
    SERVER_STOP: managed/recognized target identifier.
  STATE: U opcode, U carrierUUID, U setupState, U role, U providerType,
    U configuredBoolean, U lastTestSummary. This is state feedback, not a durable ACK.
  FEEDBACK: U opcode, U carrierUUID, U message.
  OPEN: U opcode, U page/action (e.g. SETUP, STAFF, CLAIM_OWNER).
  TEST_START: U opcode, U destinationID, U statusTarget; Core's legacy handler uses
    the third field as its target after administrative authorization.
  COUNTDOWN_FEEDBACK: U opcode, U message, B playSound, U sound, F volume, F pitch.
  DISCOVERY_ADD: U opcode, I count, repeated U Velocity target, U destination ID,
    U status target. Hub accepts count 0..500 and adds missing destination IDs.
  GUI command routing uses OPEN with U "GUI:" + command arguments joined by U+001F.
    UnifiedGuiBridge splits that field and calls HubPilotGuiCommand.onCommandLegacy;
    PublicGuiRouter/DirectOpenTransport supply the matching send path.

hubpilot:status:
  Hub -> Core: U STATUS_SYNC_REQUEST.
  Core -> Hub: U STATUS_ROW, U managedID, U state, L onlineSince, L lastStarted,
    L lastChecked, I playersOnline, I playersMax, L backendPingMs, I queueSize,
    L startRequestedAt, I expectedStartupSeconds, U lastError (truncated to 512).
  Core -> Hub: U STATUS_SYNC_END.
  Hub's END handler refreshes an open Navigator. Rows have no transaction ID,
    generation or negotiated schema version. An END is not proof of an atomic
    cross-store snapshot or an acknowledged committed settings change.

hubpilot:settings:
  Hub -> Core: U SETTINGS_SNAPSHOT, U Java-properties text.
  Core rejects empty payloads / payloads >65535 bytes, text >50000 characters;
    accepts only known keys and values <=1024 characters; writes format-version=2.
  Key families are global.<allowed-setting>, server.<normalized-id>.<allowed-setting>
    and permitted message keys. See SettingsSyncHook.validKey / ALLOWED and
    OperatingModeRules.addAllowed for the exact allowlist; do not replace it with
    an unrestricted file/config write endpoint.
  The accepted set REPLACES the synchronized properties snapshot, not an optimistic
    per-key merge. Equal snapshots avoid a write. Temp-file/atomic-move fallback is
    used. Core reload applies the effective result.
  There is no explicit per-update acknowledgement, revision conflict protocol or
    replay nonce. Server trust is checked; this hook is not a per-user owner check.
    Hub sends settings when requesting status, using any connected player's carrier.
    Therefore carrier identity alone is not the authority for settings editing.
    Local Hub editing/file access is part of this trust boundary.

hubpilot:telemetry, protocol 1:
  Link -> Core LINK_HEARTBEAT: U opcode, I protocol=1, U platform, U minecraftVersion,
    U linkVersion, D tps, D mspt, L memoryUsedMb, L memoryMaxMb, D cpuPercent,
    I loadedChunks, I entities, I players, B ready.
  Hub -> Core: U TELEMETRY_SYNC_REQUEST.
  Core -> Hub TELEMETRY_ROW: U opcode, I protocol=1, U managedID, L backendPingMs,
    I queueSize, I startupProgress, L averageStartupSeconds, L requests,
    L successfulJoins, L failedJoins, U lastError, L carrierPlayerPingMs,
    B linkPresent, L heartbeatReceivedAt, U platform, U minecraftVersion,
    U linkVersion, D tps, D mspt, L memoryUsedMb, L memoryMaxMb, D cpuPercent,
    I loadedChunks, I entities, I players, B ready.
  Core -> Hub: U TELEMETRY_SYNC_END, I protocol=1.
  Core bounds telemetry strings/numbers and identifies the reporting backend from
    ServerConnection. Snapshot requests require trusted hub/request-server status;
    heartbeats are not treated as owner privileges.

hubpilot:auth is registered by Core; active AUTH/COMPONENT/ACTION handling inspected
here is on hubpilot:control. Do not invent a second authenticated wire protocol just
because the registered channel name exists.

Trust and replay scope:
  Core handles relevant messages instead of forwarding them to clients, requires
    a server-side connection for normal requests/auth, and rejects client-origin
    traffic on these paths. Request sources must be trusted-request-servers.
  AUTH/ACTION require the configured hub and a payload UUID matching the carrier.
  Hub checks UUID equality on STATE/FEEDBACK before applying them to a player.
  Settings/status hooks trust configured backend identities, not a message signature.
  AUTH freshness is 15 seconds in AccessManager; this is not replay protection for
    arbitrary actions. No general nonce, sequence, HMAC or idempotency ledger was
    found for request/settings/action traffic.
  A compromised trusted hub remains a powerful trust boundary. Correct forwarding,
    proxy-only backend access and control over installed plugins are prerequisites.
  No full malicious-payload or replay campaign was run during this audit. Do not
    label this protocol security-audited based only on the checks above.

Roles on both sides:
  Core stores owners and staff by UUID in staff.yml. Owners are explicit; OP or a
    LuckPerms group does not silently become owner. First claim requires an unowned
    install plus recent configured-hub auth with OP or hubpilot.claimowner.
  AccessManager.role prefers owner, then stored staff role, then fresh Hub direct
    admin/moderator/helper report, then configured OP fallback, else player.
    op-default-role supports none/helper/moderator/admin. Default admin is not owner.
  Core role permissions/inheritance live in permissions.yml. Owner-only provider
    credential/setup/owner operations explicitly check owner; SERVER_STOP checks
    hubpilot.servers.stop; command gates use role checks and some platform nodes.
  Hub reads Bukkit/LuckPerms nodes and OP, reports them in AUTH and gates local UI
    actions. Built-in roles returned in STATE also drive local access.
  Interact edit permission is separate from general Core ownership. Its editor
    recognizes its nodes and Hub role support; validate every edit/command path.
  A configured destination's join permission is checked with Velocity
    player.hasPermission, not automatically with Hub's role permission list.
    Do not assume every arbitrary Bukkit-only permission is propagated to Velocity.
  Built-in roles and native platform permissions overlap but are not one universal
    permission service. Do not replace Core checks with trusting a visible GUI item.

Refresh timing (defaults / inspected scheduling):
  Core lifecycle tick 1 second; status polling default 5 seconds; config reload
    default 3 seconds; statistics save every 60 seconds plus shutdown.
  Core status-file write is scheduled roughly 1 second after refresh dispatch; it
    does not await a single aggregate future for all pings.
  Hub status/telemetry request every 20 ticks with a carrier; AUTH heartbeat every
    20 ticks; local store reload timer 40 ticks; Navigator item repair 100 ticks.
  Link heartbeat every 20 ticks, only while at least one player is connected.
  These Bukkit tick intervals stretch under server lag. No carrier means no plugin
    message delivery; absence of Link data is not proof of a stopped server.
    TelemetryStore marks linkPresent=false after 10 seconds but retains prior values;
    consumers must consider age/presence rather than displaying stale metrics as live.

    in a hot-reloaded config does not visibly recreate those tasks.

  PublicDefaults seeds shared-directory: shared. Older fallback literals still name
    /shared/hubpilot; inspect the actual generated config and resolved process working
    directory. A relative path is not automatically the same mount in both processes.
  Defaults documented for lifecycle are expected startup 60s, startup timeout 120s,
    ping timeout 3s, three retries delayed 15s, idle timeout 30min, countdown 5s,
    strict-version=false, stop-after-failure=true, stop-when-queue-empty=true.
    Server/YAML/property overrides and hub/Always-On protection can change them.
  Core constructs YAML server values from defaults.yml plus servers/<id>.yml, then
    applies global/per-server hubpilot.properties overrides for supported fields.
    Per-server property beats global property; absent property falls back to YAML.
    Always-On then forces effective automatic-stop flags off (and autostart on).
    Configured-hub repair runs after those settings and preserves startup preference.
  Message file defaults/legacy strings and permitted GUI message overrides feed
    QueueMessages. Invalid/unknown synchronized keys must remain filtered.

    reload logs rejection and retains the previous snapshot. Duplicate managed IDs
    reject reload. Provider/access managers also reload their own files by mtime.
    This is not one atomic transaction across all stores/managers.

    files. A real common mount can share the directory; otherwise plugin-message
    settings/status/discovery paths supply selected synchronization, not a full
    distributed filesystem. Hub also has a writable local fallback.

    every file is mirrored without it. Keep one authoritative Hub settings writer;
    multiple writers or stale snapshots can overwrite each other with no revision
    arbitration. Multi-hub editing is not a solved current feature.

5. PROVIDERS AND DISCOVERY

IMPLEMENTED: CraftyProvider.start/stop adapts ProviderRegistry.action to ActionResult.
Despite the class name/log wording, provider definitions can select Crafty,
Pterodactyl, Generic HTTP or Always-On. ProviderRegistry.Definition contains id,
type, enabled, baseUrl, secretKey, insecure, timeout and values. Result contains
success, statusCode and error. action uses CompletableFuture.supplyAsync and the
implementation performs blocking HTTP within that asynchronous task.

Crafty:
  GET <base>/api/v2/servers for inventory/test.
  POST <base>/api/v2/servers/<url-encoded-panel-UUID>/action/start_server
  POST <base>/api/v2/servers/<url-encoded-panel-UUID>/action/stop_server
  Bearer token; base URL should be panel root, not already suffixed /api/v2.
  Panel server UUID is not its friendly name or Velocity ID. Account visibility and
    server permissions determine inventory/control. docs/PROVIDERS.md records a
    permissions problem with a COMMANDS-only test and successful fuller access;
    reproduce needed scope on the installed Crafty version, not a universal owner-
    credential requirement. Never put real credentials into tests or GitHub.

Pterodactyl:
  Client API credential, not Application API credential.
  POST <base>/api/client/servers/<encoded-identifier>/power
  JSON body {"signal":"start"} or {"signal":"stop"}; Bearer authentication.
  Provider test uses /api/client. An HTTP test PASS does not prove a specific server's
    power permission or successful player connectivity.

Generic HTTP:
  Configurable start-url/stop-url, methods (default POST) and bodies.
  {server} in URLs is encoded; substitution in bodies is raw providerServerId.
    It is not an automatic JSON-escaping/template validation layer.
  status-url is optional and used by provider test; it is not a full normalized
    backend readiness implementation replacing Velocity ping.
  Auth types: none, bearer, x-api-key, basic; custom header.* values supported.
  Without status-url, test() returns a synthetic successful 204 without an HTTP
    request. The same shortcut exists for Always-On. A displayed Connected/204 is
    therefore not necessarily an observed response from a remote server.

Always-On provider:
  No controllable process; power requests fail rather than starting offline servers.
  Keep this separate from Always-On server flag on a controllable provider.

Credential/TLS behavior:
  Provider definitions resolve secret-key through secrets.yml; whole-value ${ENV}
    substitution is supported. Do not assume arbitrary embedded interpolation.
  Legacy migration can resolve older Crafty token-file configuration. Describe that
    reference only; do not publish token file contents.
  Writing secrets attempts owner-read/write POSIX permissions where supported.
  ProviderHttpSupport is the active send path. Normal HTTPS uses certificate and
    hostname validation. Explicit allow-insecure-tls uses a per-connection
    HttpsURLConnection trust-all certificate manager and hostname verifier.
    Redirect following is disabled there; normal HttpClient also does not opt into
    redirect following. Do not make insecure TLS a public default.
  Request and connect timeout use provider timeout, default 10 seconds in docs;
    insecure transport sets connect/read timeouts. Provider responses accept 2xx,
    treat other HTTP statuses as failure and compact the returned body for errors.
  No application-level exponential backoff, Retry-After policy, idempotency key or
    durable command ledger is implemented in this action transport. A timeout can
    be an unknown outcome after the panel accepted an action; blindly retrying may
    issue it twice. Lifecycle connection retries are a different mechanism.
  Success means HTTP acceptance, not process readiness or completed shutdown.
  HTTP response bodies are collected before compaction, not bounded by a small
    streaming response cap in the inspected transport. Error-body redaction is not
    proven comprehensive; do not paste unreviewed panel errors into public reports.

Discovery identity/persistence:
  CraftyDiscoverySupport reads aliases for ID/name/host/port in returned inventory.
  Name canonicalization lowercases and removes non-alphanumerics for matching;
    Velocity names use a sanitized hyphen form. Existing managed IDs, Velocity names,
    labels and panel IDs are considered in matching/repair paths. Colliding friendly
    names must be tested; a display label is not a unique identity.
  Wildcard/loopback/missing panel-reported hosts can fall back to panel URL host.
    That can be wrong across NAT, separate container networks or port mappings.
    An API-visible port alone does not establish proxy reachability.
  DynamicServerRegistry registers missing Velocity names and persists endpoints in
    dynamic-servers.properties; restore runs during public bootstrap.
  Existing registered Velocity names are not replaced by register(). A changed
    address may be saved in discovery persistence while current registration remains
    old. Do not assume rediscovery live-updates all endpoints or prunes deleted ones.
  HubPilotConfig handles managed mapping/duplicate repair and backups;
    DiscoveryNavigatorBridge/DiscoveryAliases coordinate Navigator cleanup/cache.
    Preserve original managed identity and user customization when testing migration.
  Configured-hub exclusion and protection use normalized ID/Velocity name, not
    arbitrary substring matching on labels. HubProtection removes punctuation/case,
    with optional 'the'/'main' prefixes and 'server' suffix equivalence. Test unusual
    collisions; do not broaden the guard to every server containing 'hub'.
